[SECTION: AbstractionGuidance]
### ABSTRACTION GUIDANCE:

**THE WHAT/HOW TEST** - stated once here; every other section that needs it cites it by this name rather than restating it.
Does the statement describe WHAT the system must do, or HOW to encode it in Alloy?
- WHAT - observable behaviour, obligation, permission, timing, cardinality. It belongs to the requirements.
- HOW - which signature, field, predicate, function, assertion, variable, operator, or bound to use. It is a modeling choice: it belongs in repair instructions or a lesson, and never in a question to the user.

**Applying the test to user questions** - ask only when the answer changes what must be verified.

Ask when:
- Behavioral ambiguity affects verification
- Cardinality affects consistency
- Temporal ordering matters
- Missing scenarios need confirmation
- A requirement may be ambiguous, inconsistent, incomplete, or logically weak.


Do not ask when:
- the candidate is a HOW,
- the detail can be safely abstracted,
- different answers would not change the verification structure.

### DEFAULT ASSUMPTION POLICY
If the user does not answer a clarification question, continue with the smallest reasonable assumption.

Use the weakest assumption that:
- is enough to proceed,
- preserves the abstract requirement intent,
- and adds no unnecessary constraints or behavior.

State the assumption explicitly and treat it as provisional.

- Review modeling assumptions
- Identify unnecessarily strong assumptions

- Recommend stronger assertions when current ones are weak

### REQUIREMENT-CHANGE TRIAGE (run before writing ANY change)

A candidate change may come from a verification finding or from user feedback.
Before proposing it, SCAN THE FULL current requirements document provided (all
R#/R#.# and every [E#] bullet) and classify into EXACTLY ONE bucket, citing the
item ID(s) you relied on:

1. DUPLICATE - already stated by an existing item (fully or in substance;
   rephrasing/splitting counts) → no change; name the covering ID (e.g. "covered
   by R4.3").
2. MODELING - describes HOW to model (signature/field/predicate/variable/bound/
   operator), not WHAT the system does → route to REPAIR INSTRUCTIONS, never the
   document.
3. CONSTRAINT - restricts/verifies already-required behavior, is a consequence of
   an existing requirement, or is verification/scenario-only (coverage witnesses,
   scope bounds) → CONSTRAINTS bullet, not a new R#; check it is not a DUPLICATE of
   an existing [E#].
4. REQUIREMENT - a genuinely NEW capability/obligation → if it qualifies exactly
   one existing R_n, add as sub-requirement R_n.k under that parent; else new
   top-level R#.
5. UNSURE - cannot confidently choose (usually requirement-vs-constraint, or which
   parent) → write nothing this iteration; raise a question in UPDATED USER
   QUESTIONS prefixed with `[CLASSIFICATION]`, stating the candidate and the
   readings you are choosing between (e.g. new requirement vs constraint vs
   modeling note).
6. CONTRADICTS - an existing item cannot hold at the same time as this candidate:
   obeying one violates the other (NOT merely "different", "narrower", or "about
   the same topic" - two requirements that can both be satisfied are
   COMPLEMENTARY, not contradictory) → name the MINIMAL set of existing item IDs
   it conflicts with in `Conflicts with:`, and state in one line why they cannot
   both hold. Name BOTH SIDES: the ids it conflicts with, and the concrete id
   this candidate will become, stated in `Target kind & placement` and repeated
   in `Recommended Update`. A conflict whose own side is described only in prose
   ("the session-handling change") cannot be attached to the requirement it is
   about, and is dropped.

Confirm the CLASSIFICATION/PLACEMENT, not wording the user just gave. Never default
an unclassifiable candidate to REQUIREMENT - use bucket 5 and ask.

On bucket 6, err toward NOT declaring a contradiction. A missed one surfaces later
as a verification failure, with evidence; a wrongly declared one sends the user a
claim about their requirements that nothing has checked. If you cannot name the
specific existing IDs that conflict, it is not bucket 6.

A CONTRADICTS declaration does NOT hold the update back. Still write the update
exactly as you would otherwise - it is applied, encoded, and verified like any
other, and the solver decides whether the two requirements can actually coexist.
Declaring the conflict records what to check and what to ask if verification
fails; it is not a veto, and it is not a reason to soften or omit the change.
