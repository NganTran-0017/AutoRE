[SECTION: AbstractionGuidance]
### ABSTRACTION GUIDANCE:
Does the statement describe WHAT the system must do, or HOW to encode it in Alloy?
- WHAT - observable behaviour, obligation, permission, timing, cardinality. It belongs to the requirements.
- HOW - which signature, field, predicate, function, assertion, variable, operator, or bound to use. It is a modeling choice: it belongs in repair instructions or a lesson, and never in a question to the user.

Ask only when the answer changes what must be verified.

Ask when:
- Behavioral ambiguity affects verification
- Cardinality affects consistency
- Temporal ordering matters
- Missing scenarios need confirmation
- A requirement may be ambiguous, inconsistent, incomplete, or logically weak.

Do not ask when:
- the candidate is a HOW,
- the detail can be safely abstracted,
- different answers would not change the verification structure.

### DEFAULT ASSUMPTION POLICY
If the user does not answer a clarification question, continue with the smallest reasonable assumption.

Use the weakest assumption that:
- is enough to proceed,
- preserves the abstract requirement intent,
- and adds no unnecessary constraints or behavior.

State the assumption explicitly and treat it as provisional.

### UNOWNED BLOCKING FACTS - how to resolve the finding above
Each listed fact is PROVEN to block a scenario while declaring no requirement. Do not re-argue
whether it blocks, and never weaken it - a weakened fact that owns no requirement blocks again.

Decide what each fact IS, by what it actually constrains:
- behaviour the EXISTING system already guarantees -> `existing-system requirement`; name the `E#`
- structural well-formedness (unique key, total relation, no dangling reference) -> `structural well-formedness`
- scope or universe setup -> `scope/universe setup`
- behaviour of the PROSPECTIVE component -> `prospective behaviour - does not belong in a fact`; name the `R#`
- nothing you can name -> `delete`

Decide WHAT the fact is, not how to encode it.
Classify EVERY listed fact before concluding anything - do not stop at the first one you can
explain. The set matters: several existing-system rules may block one scenario together, and only
the full list identifies the real conflict.

A fact classified `existing-system requirement` is legitimate and STAYS - but it is still provably
blocking a prospective scenario, so it is also a requirement finding:
- Quote the requirement text you matched it to. A fact you cannot tie to text is not an `E#` - it
  is an artifact, and its resolution is `delete`.
- First confirm the witness predicate is not stronger than the requirement it witnesses. An
  over-specified witness conflicts with a scenario the model invented, not with the requirements -
  that is a model defect, not a requirement conflict.
- Then name every `E#` in the blocking set under `=== POTENTIAL REQUIREMENT ISSUES ===` as an
  `inconsistency` with the prospective requirement whose witness they block, and ask the user which
  gives way under `=== UPDATED USER QUESTIONS ===`. An `E#` is given ground truth about the existing
  system, so only the user can settle it - ask under EVERY strategy.

Record ONE decision per listed fact under `=== UNOWNED BLOCKING FACT DECISIONS ===`,
before any other repair instruction; an omitted fact is unresolved and is flagged again next iteration.
Required under EVERY strategy: an undeclared fact is a bookkeeping defect, not a requirements
diagnosis and not a repair hypothesis.
A fact listed under ESCALATION survived your last instruction, so do not repeat it - choose a
DIFFERENT resolution, or delete the fact.

[SECTION: RequirementChangeTriage]
### REQUIREMENT-CHANGE TRIAGE (run before writing ANY requirement change)

Before proposing a change - from a verification finding or from user feedback - scan the FULL
requirements document (every R#/R#.# and every [E#]) and classify it into EXACTLY ONE bucket,
citing the ID(s) you relied on. Only buckets 3 and 4 change the document.

1. DUPLICATE - already stated by an existing item, fully or in substance (rephrasing or splitting
   counts) -> no change; name the covering ID (e.g. "covered by R4.3").
2. MODELING - describes HOW to model (signature/field/predicate/variable/bound/operator), not WHAT
   the system does -> no document change; it belongs in the repair instructions.
3. CONSTRAINT - restricts or verifies already-required behaviour, follows from an existing
   requirement, or is verification-only (coverage witnesses, scope bounds) -> a CONSTRAINTS bullet,
   not a new R#; check it is not a DUPLICATE of an existing [E#] or constraint.
4. REQUIREMENT - a genuinely NEW capability or obligation -> if it qualifies exactly one existing
   R_n, a sub-requirement R_n.k; otherwise a new top-level R#.
5. UNSURE - you cannot confidently choose (usually requirement-vs-constraint, or which parent) ->
   change nothing and ask, prefixed `[CLASSIFICATION]`, naming the candidate and the readings you
   are choosing between. Never default an unclassifiable candidate to REQUIREMENT - use this bucket.
6. CONTRADICTS - an existing item and this candidate cannot both hold: obeying one violates the
   other. Here, err toward NOT declaring it - if you cannot name the specific conflicting IDs, it is
   not bucket 6. When it is, Name BOTH SIDES in `Conflicts with:` - the MINIMAL set of IDs it
   conflicts with, and the concrete id this candidate becomes (`Target kind & placement`) - plus one
   line on why. A side given only in prose is dropped. Declaring a contradiction does NOT hold the change
   back - write it as you otherwise would; it records what to check if verification fails.

Confirm the CLASSIFICATION and PLACEMENT, not the wording the user just gave you. The field names
above belong to the feedback format; when patching the document instead, the same classification
decides the operation and buckets 1, 2 and 5 emit none.
