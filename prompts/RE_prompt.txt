[SECTION: AbstractionGuidance]
### ABSTRACTION GUIDANCE:

Ask for clarification when:
- Core behavior is ambiguous
- Cardinality/multiplicity unclear
- Temporal ordering ambiguous
- State transitions unclear
- Exclusivity/dependency relationships undefined

Do NOT ask when:
- Implementation details (abstract as actions/privileges)
- Specific values/content (model as abstract sets)
- Multiple choices lead to same abstract model

### DEFAULT ASSUMPTION POLICY

If the user does not answer a clarification question, continue modeling the requirements with the smallest reasonable assumption.

Use the weakest assumption that:
- is sufficient to proceed,
- preserves the abstract requirement intent,
- and adds no unnecessary constraints or behavior.

State the assumption explicitly and treat it as provisional.

[SECTION: BuildAlloyModel]
### TASK: BUILD ALLOY MODEL

Create a formal Alloy 6 model from the requirements document.

**Your objectives:**
1. Translate requirements into formal Alloy 6 model at abstract level.
2. Model existing system only to extent needed for verification context.
3. Model all prospective behaviors, properties, and interactions.
4. Use facts ONLY for existing-system assumptions, structural rules, and enforced semantics. Do NOT encode a prospective requirement or an unverified assumption as a fact (see MODELING DISCIPLINE under Facts below).
5. Use predicates for operations, scenarios, transitions, and edge cases.
6. Use assertions for properties to verify.
7. Keep model abstract, syntactically valid, focused on verifying the prospective behaviors and properties.

### ALLOY MODELING GUIDELINES:

Model STRUCTURE, BEHAVIOR, and CONSTRAINTS, not implementation.
The model must be syntactically valid Alloy 6.
1. Signatures: Clear names, careful multiplicities (one/lone/some/set)

2. Facts: Encode existing-system assumptions, baseline rules, structural constraints
   - MODELING DISCIPLINE (binding): facts hold ONLY the existing system's requirements and assumptions that must always hold. Prospective requirements are modeled as predicates (R1, R1R2, ..., All_Requirements) and assertions, and are NEVER promoted to facts during verification - even when feedback says to "enforce" or "strictly require" them: strengthen the requirement's PREDICATE (or ASSERTION) instead. Any assumption YOU introduce is modeled as a SEPARATE predicate named A1, A2, A3, ... (each with its own `run`), NOT as a fact, because it may conflict with the model in ways not foreseen before verification. A fact applies globally, so one inconsistent unverified constraint in a fact makes the ENTIRE model - including `baseline` - UNSAT and destroys diagnosability. An assumption predicate A_k is promoted to `fact A_k` automatically only after it verifies SAT for at least 2 consecutive iterations; never hand-promote an assumption earlier, and never promote a prospective requirement at all.

3. Predicates: Define scenarios and transitions, verify with `run`
   - Create an empty `baseline` predicate to verify the existing system requirements (which are modeled as facts). `baseline` checks the EXISTING system only - it must never contain or be constrained by any prospective requirement or unverified assumption.
   - Name prospective requirement predicates incrementally: R1, R1R2, R1R2R3, etc.
   - Name user-introduced assumption predicates A1, A2, A3, ... - kept SEPARATE from R* so they can be verified independently and, after 2 consecutive SAT iterations, auto-promoted to facts. Add a `run` for each (place after `run baseline`).
   - Name most comprehensive predicate: All_Requirements (contains all prospective requirements R1+R2+R3+...)
   - Run commands MUST follow this order:
     1. `run baseline` - verify existing system (facts) alone is satisfiable
     2. `run All_Requirements` - most comprehensive predicate first
     3. `run R1`, `run R1R2`, `run R1R2R3`, etc. - incremental predicates for localization
     4. `check assert...` - assertions to verify properties

4. Assertions: State properties to verify, check with `check`
   - Name assertions with a prefix `assert[name]`

5. Best Practices:
   - Prefix with requirement IDs (e.g., fact R1R2, pred R3, assert assertR4)
   - Every fact must declare the requirement it encodes: carry the ID in its name, or put `//@req <IDs>` on its declaration line (R# for emergency-module, E# for existing-system requirements; comma-separate multiple). A fact constrains every run, so an undeclared one, or one naming a requirement that no longer exists, is treated as stale.
   - Assertions and run-invoked predicates should declare theirs the same way; an exploratory or edge-case check that encodes no requirement is valid - mark it `//@req none:probe`.
   - Helper functions and predicates need no declaration - ownership is derived from the constructs that call them.
   - Other constructs that deliberately encode no requirement: `//@req none:frame` (well-formedness) or `//@req none:harness` (scope/universe setup).
   - Use Alloy 6 temporal modeling for time/state (var for mutable properties)
   - Place all `open` statements at top
   - Verify incrementally with predicates
   - Use `'` to denote the next state without declaring


6. Avoid:
   - Over/under-constraining
   - Omitting relevant existing-system assumptions
   - Circular definitions
   - Incorrect multiplicities
   - Missing transitive closure (^, *)
   - Unnecessary implementation details
   - Placing verifiable properties in facts
   - Using True/False as boolean values

### TASK: DIAGNOSTIC EXPERIMENTS

This iteration is a MEASUREMENT, not a repair. Its deliverable is evidence about which
construct causes the failure - not a better model. The Evaluator chose it because it cannot
tell which of several constructs is responsible, and a run would tell it.

Work ONLY from the `=== DIAGNOSTIC PLAN ===` section of the feedback, plus any experiments
re-issued under `STRATEGY: RERUN_DIAGNOSTIC_PROBES` in the Cross-Iteration Escalation Status
above (those were ordered last iteration and produced no probe; they belong to this
iteration's plan and continue its numbering). Every item has a construct, a hypothesis, and a
reading declared BEFORE the run. Do not invent experiments, and do not act on the
`=== DIAGNOSTIC CANDIDATES ===` section - those were not adopted.

**How to express an experiment - as a probe, never as an edit:**
1. For each plan item, ADD a predicate named `probe<N>_<Target>` (N = the item's position in
   the plan) that restates the failing scenario with the hypothesised constraint altered -
   relaxed, removed, or replaced - exactly as the hypothesis describes.
2. Mark it `//@req none:probe` on its declaration line, and give it its own `run` command at
   the same scope as the scenario it mirrors. That run command IS the experiment: its
   SAT/UNSAT verdict is the measurement, so you record nothing yourself.
3. One hypothesis per probe. Two altered constraints in one probe cannot be told apart, which
   is the failure this mode exists to prevent.
4. A probe is reachable ONLY from its own `run`. Never call it from another predicate, never
   add it to `All_Requirements`, never reference it in an assertion or an R-chain.

Alloy cannot parameterise over predicates, so a probe duplicates the scenario body. That is
accepted: probes live exactly one iteration and are deleted next iteration.

**Forbidden - these turn a measurement into an undeclared repair:**
- **DO NOT modify ANY existing construct.** Not the ones named in the plan, not their
  helpers, not a scope, not a run command. The production model changes ONLY by addition. A
  construct carrying `//@req R#` or `//@req E#` encodes a requirement; altering it makes the
  next verification measure a model nobody approved, and its ownership annotation becomes a
  lie.
- **DO NOT delete anything**, including constructs you believe are the cause. Deleting is the
  repair the experiment is meant to justify, not the experiment.
- **DO NOT fix the failing scenario**, even if the cause looks obvious while you write the
  probe. Say so in your report instead; the Evaluator decides the repair once it has the
  measurement.
- **DO NOT run more than one experiment inside one probe**, and do not skip a plan item
  because you expect its answer.

**If a plan item cannot be executed** - the construct is not where the plan says, the
hypothesis cannot be expressed as an additive probe, or two items would collide - write the
probe you can and report the one you cannot, with a one-line reason. Reporting a skip is
correct; silently omitting it is not, because an item that produces no verdict is
indistinguishable from an experiment that returned UNSAT.

**Items already answered:** the `=== DIAGNOSTIC ITEMS NOT RUN (already measured) ===` block,
when present in the Cross-Iteration Escalation Status above, lists plan items the workflow
removed because the deterministic diagnosis has already measured them. Do NOT write probes
for those. Copy each into your report as `Executed: no` with the reason given, so the
Evaluator receives the measured status rather than silence.
