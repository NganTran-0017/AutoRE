[SECTION: AbstractionGuidance]
### ABSTRACTION GUIDANCE:

Ask for clarification when:
- Core behavior is ambiguous
- Cardinality/multiplicity unclear
- Temporal ordering ambiguous
- State transitions unclear
- Exclusivity/dependency relationships undefined

Do NOT ask when:
- Implementation details (abstract as actions/privileges)
- Specific values/content (model as abstract sets)
- Multiple choices lead to same abstract model

### DEFAULT ASSUMPTION POLICY

If the user does not answer a clarification question, continue modeling the requirements with the smallest reasonable assumption.

Use the weakest assumption that:
- is sufficient to proceed,
- preserves the abstract requirement intent,
- and adds no unnecessary constraints or behavior.

State the assumption explicitly and treat it as provisional.

[SECTION: BuildAlloyModel]
### TASK: BUILD ALLOY MODEL

Create a formal Alloy 6 model from the requirements document.

**Your objectives:**
1. Translate requirements into formal Alloy 6 model at abstract level.
2. Model existing system only to extent needed for verification context.
3. Model all prospective behaviors, properties, and interactions.
4. Use facts for existing system assumptions, structural rules, and enforced semantics. Do not encode a requirement as a fact unless it is intentionally assumed to be true at all time.
5. Use predicates for operations, scenarios, transitions, and edge cases.
6. Use assertions for properties to verify.
7. Keep model abstract, syntactically valid, focused on verifying the prospective behaviors and properties.

### ALLOY MODELING GUIDELINES:

Model STRUCTURE, BEHAVIOR, and CONSTRAINTS, not implementation.
The model must be syntactically valid Alloy 6.
1. Signatures: Clear names, careful multiplicities (one/lone/some/set)

2. Facts: Encode existing-system assumptions, baseline rules, structural constraints

3. Predicates: Define scenarios and transitions, verify with `run`
   - Create an empty `baseline` predicate to verify the existing system requirements (which are modeled as facts)
   - Name prospective requirement predicates incrementally: R1, R1R2, R1R2R3, etc.
   - Name most comprehensive predicate: All_Requirements (contains all prospective requirements R1+R2+R3+...)
   - Run commands MUST follow this order:
     1. `run baseline` - verify existing system (facts) alone is satisfiable
     2. `run All_Requirements` - most comprehensive predicate first
     3. `run R1`, `run R1R2`, `run R1R2R3`, etc. - incremental predicates for localization
     4. `check assert...` - assertions to verify properties

4. Assertions: State properties to verify, check with `check`
   - Name assertions with a prefix `assert[name]`

5. Best Practices:
   - Prefix with requirement IDs (e.g., fact R1R2, pred R3, assert assertR4)
   - Use Alloy 6 temporal modeling for time/state (var for mutable properties)
   - Place all `open` statements at top
   - Verify incrementally with predicates
   - Use `'` to denote the next state without declaring


6. Avoid:
   - Over/under-constraining
   - Omitting relevant existing-system assumptions
   - Circular definitions
   - Incorrect multiplicities
   - Missing transitive closure (^, *)
   - Unnecessary implementation details
   - Placing verifiable properties in facts
   - Using True/False as boolean values

### TASK: SYNTAX-ONLY MODEL REPAIR

Fix the current syntax/type error with MINIMAL changes.

**CRITICAL CONSTRAINTS:**

1. **Address ONLY the specific syntax/type error** identified in the Evaluator feedback
2. **Make the SMALLEST possible change** to resolve the error - do not refactor unrelated code
3. **DO NOT reinterpret requirements** or add new domain assumptions
4. **DO NOT add/modify/remove facts, predicates, or assertions** unless directly involved in the syntax error
5. **DO NOT strengthen or weaken behavior** unless absolutely required for type correctness
6. **Preserve all existing model semantics** - the model's meaning should remain unchanged

**Allowed Changes:**
- Fix syntax errors (missing braces, parentheses, brackets, semicolons, etc.)
- Fix type errors (correct type annotations, fix multiplicity errors)
- Refactor predicate to function (or vice versa) ONLY if required by type system
- Minimal local edits to resolve parsing/compilation errors

**Forbidden Changes:**
- Adding new facts, predicates, assertions, or run/check commands unrelated to the error
- Modifying constraints, signatures, or fields not directly involved in the syntax error
- Reinterpreting requirements or changing model behavior
- "Improving" the model structure, naming, or organization
- Making semantic changes while fixing syntax

**MULTI-LOCATION PATTERN FIX (applies when the Evaluator feedback lists more than one affected location for the same error pattern):**
The Alloy analyzer reports only the first error, but the same root-cause pattern often recurs in other blocks. When the [REPAIR INSTRUCTIONS] enumerate several locations (an "Affected locations (same pattern)" list, or steps naming multiple blocks) exhibiting the SAME error pattern:
- Correcting EVERY listed occurrence is REQUIRED and COUNTS as addressing the reported error - it is NOT forbidden refactoring and does NOT violate the minimal-change constraint.
- Apply the IDENTICAL correction consistently to all listed sites in this one update, so the same error does not resurface block-by-block on later iterations.
- The minimal-change constraint still applies to everything else: do NOT touch any code that is not one of the listed occurrences.

**USER-DIRECTED FIX OVERRIDE:**
If the Evaluator feedback contains a [USER GUIDANCE COMPLIANCE] section, the repair originates from the HUMAN USER after repeated automated attempts failed. In that case:
- Apply EVERY repair step in full - including construct replacements (e.g., replacing a fun with a pred), new `open` statements, and updates to all call sites of a changed construct. These count as addressing the error, not as forbidden refactoring.
- Implementing the user's fix completely takes precedence over the minimal-change constraint. Do not partially apply it, keep the old construct alongside the new one, or downgrade any step.
- Everything unrelated to the user-directed fix must still remain unchanged.

**ESCALATION OVERRIDE (read the Cross-Iteration Escalation Status above):**
- If it lists PREVIOUSLY ATTEMPTED FIXES, none of those edits may be re-applied - they already failed, even if the Evaluator feedback appears to suggest one of them again.
- If STRATEGY is REWRITE_BLOCK, the minimal-change constraint is LIFTED for the block named under AFFECTED BLOCK (and only for that block): rewrite that entire block from scratch per the Evaluator's instructions, preserving its intended meaning and using the simplest valid Alloy 6 constructs, while leaving the rest of the model unchanged.
- If STRATEGY is REGENERATE_BLOCK, DELETE the block named under AFFECTED BLOCK entirely and write a replacement derived from the LATEST REQUIREMENTS attached to the escalation directive - NOT from the old block text (it has resisted repair and is not a usable starting point). Preserve the block's name and parameters unless the Evaluator's instructions say otherwise; if the interface must change, update every block that references it. The minimal-change constraint is lifted for this block and its call sites only.
- If STRATEGY is REQUIREMENTS_DIAGNOSIS, apply the Evaluator's INTERIM repair exactly as instructed (it may simplify the block or temporarily comment it out with a TODO); the requirement-level fix will arrive through the updated requirements document in a later iteration.
- If STRATEGY is BREAK_OSCILLATION, make one coherent change that resolves both the current error and the error listed under OSCILLATING WITH ERROR; do not fix one at the expense of re-introducing the other.
